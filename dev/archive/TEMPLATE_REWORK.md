# Template System Rework Implementation Plan - Simplified

## 1. Overview

This document outlines the implementation plan for refactoring BenchPRO's template system to create a more modular, maintainable, and user-friendly approach to script generation. The new system will shift from requiring users to write complete script templates to a block-based composition system where users only need to provide the task-specific commands.

### 1.1 Core Objectives

- Simplify user templates by removing boilerplate
- Create a modular block-based composition system
- Support different execution contexts (local, SLURM) without duplicating templates
- Enable easy addition of functionality like module loading and environment setup
- Focus on clean, minimal code with no unnecessary complexity

### 1.2 Current Limitations

The current template system has several limitations:

1. **User Template Complexity**: Templates contain significant boilerplate (shebang, timestamp logging, workspace handling)
2. **Duplication**: Common patterns must be repeated in every template
3. **Maintenance Burden**: Changes to standard elements require updating multiple templates
4. **Post-Processing**: The system modifies templates after rendering (e.g., adding workspace directory handling)
5. **Context-Specific Logic**: Different execution contexts (local vs. SLURM) require special handling

## 2. Architecture Design

### 2.1 Core Components

The new template system will be built around these key components:

1. **TemplateBlock**: Base class for template content blocks
2. **TemplateCompositionEngine**: Engine for assembling blocks into complete scripts
3. **Standard Block Library**: Pre-defined blocks for common elements
4. **ComposableScriptGenerator**: Script generator using the block system

### 2.2 Design Principles

1. **Separation of Concerns**: Each block has a single, well-defined responsibility
2. **Composability**: Blocks can be assembled in different combinations
3. **Context Awareness**: Blocks can be included conditionally based on execution context
4. **Extensibility**: New block types can be added without modifying existing code
5. **Simplicity**: User templates focus only on task-specific commands
6. **Clean Code**: Minimal implementation with no unnecessary complexity

### 2.3 Block System Design

```
TemplateBlock (Abstract Base Class)
├── StringTemplateBlock (Content defined inline)
├── FileTemplateBlock (Content loaded from file)
└── FunctionTemplateBlock (Content generated dynamically)
```

Each block has:
- A name for identification
- A priority for ordering
- An execution context specification (which contexts it applies to)
- A render method that produces content given variables

### 2.4 Composition Engine Design

The composition engine:
1. Maintains a registry of blocks
2. Filters blocks by execution context
3. Orders blocks by priority
4. Renders each block with provided variables
5. Assembles the rendered blocks into a complete script

### 2.5 Integration with Task Composition

The new template system will integrate with the task composition architecture:

```
Task
├── ConfigComponent
├── ValidationComponent
├── ScriptGenerationComponent (integration point) ◄── New Template System
└── ExecutionComponent
```

## 4. Implementation Details

### 4.1 Core Block Classes

```python
from abc import ABC, abstractmethod
from typing import Dict, Any, List, Optional
from jinja2 import Template, Environment

class TemplateBlock(ABC):
    """A block of template content with a specific purpose."""
    
    def __init__(self, name: str, priority: int):
        self.name = name
        self.priority = priority
    
    @abstractmethod
    def render(self, context: Dict[str, Any], execution_context: str) -> str:
        """Render this block with the given context variables."""
        pass
    
    def applies_to_context(self, execution_context: str) -> bool:
        """Check if this block applies to the given execution context."""
        return True  # Default implementation applies to all contexts


class StringTemplateBlock(TemplateBlock):
    """A template block with static or Jinja template content."""
    
    def __init__(self, name: str, content: str, priority: int, 
                 contexts: Optional[List[str]] = None):
        super().__init__(name, priority)
        self.content = content
        self.contexts = contexts
    
    def render(self, context: Dict[str, Any], execution_context: str) -> str:
        env = Environment(trim_blocks=True, lstrip_blocks=True)
        template = env.from_string(self.content)
        return template.render(**context)
    
    def applies_to_context(self, execution_context: str) -> bool:
        if self.contexts is None:
            return True
        return execution_context in self.contexts


class FileTemplateBlock(TemplateBlock):
    """A template block that loads content from a file."""
    
    def __init__(self, name: str, file_path: str, priority: int, 
                 contexts: Optional[List[str]] = None):
        super().__init__(name, priority)
        self.file_path = file_path
        self.contexts = contexts
    
    def render(self, context: Dict[str, Any], execution_context: str) -> str:
        with open(self.file_path, 'r') as f:
            content = f.read()
            
        env = Environment(trim_blocks=True, lstrip_blocks=True)
        template = env.from_string(content)
        return template.render(**context)


class FunctionTemplateBlock(TemplateBlock):
    """A template block that generates content using a function."""
    
    def __init__(self, name: str, func, priority: int, 
                 contexts: Optional[List[str]] = None):
        super().__init__(name, priority)
        self.func = func
        self.contexts = contexts
    
    def render(self, context: Dict[str, Any], execution_context: str) -> str:
        # Call the function with the context and execution_context
        return self.func(context, execution_context)
```

### 4.2 Composition Engine

```python
class TemplateCompositionEngine:
    """Engine for composing templates from blocks."""
    
    def __init__(self):
        self.blocks = {}  # name -> block
    
    def register_block(self, block: TemplateBlock):
        """Register a template block."""
        self.blocks[block.name] = block
    
    def compose(self, context: Dict[str, Any], execution_context: str) -> str:
        """Compose a template from blocks."""
        # Get applicable blocks
        applicable_blocks = []
        for name, block in self.blocks.items():
            if block.applies_to_context(execution_context):
                applicable_blocks.append(block)
        
        # Sort blocks by priority
        applicable_blocks.sort(key=lambda b: b.priority)
        
        # Render blocks
        rendered_blocks = []
        for block in applicable_blocks:
            rendered = block.render(context, execution_context)
            if rendered.strip():  # Only include non-empty blocks
                rendered_blocks.append(rendered)
        
        # Join with newlines
        return "\n\n".join(rendered_blocks)
```

### 4.4 Script Generator Implementation

```python
class ComposableScriptGenerator(ScriptGenerationComponent):
    """Script generator that uses the template composition engine."""
    
    def __init__(self, execution_context: str):
        self.execution_context = execution_context
        self.composition_engine = TemplateCompositionEngine()
        self.logger = get_logger(__name__)
        
        # Register standard blocks
        self._register_standard_blocks()
    
    def _register_standard_blocks(self):
        """Register standard template blocks."""
        # Always include shebang
        self.composition_engine.register_block(SHEBANG_BLOCK)
        
        # Include SLURM directives for SLURM context
        if self.execution_context == "slurm":
            self.composition_engine.register_block(SLURM_DIRECTIVES_BLOCK)
        
        # Include common blocks
        self.composition_engine.register_block(WORKSPACE_DIR_BLOCK)
        self.composition_engine.register_block(MODULE_LOADING_BLOCK)
        self.composition_engine.register_block(ENV_VARS_BLOCK)
        self.composition_engine.register_block(START_TIMESTAMP_BLOCK)
        self.composition_engine.register_block(END_TIMESTAMP_BLOCK)
    
    def prepare_variables(self, config: Dict[str, Any]) -> Dict[str, Any]:
        """Prepare variables for template rendering."""
        variables = dict(config)
        variables["execution_context"] = self.execution_context
        return variables
    
    def generate_script(self, template_path: str, variables: Dict[str, Any]) -> str:
        """Generate a script using template composition."""
        # Create a template block for the user's template
        user_block = FileTemplateBlock(
            name="user_commands",
            file_path=template_path,
            priority=PRIORITY_USER_COMMANDS
        )
        
        # Register the user block
        self.composition_engine.register_block(user_block)
        
        # Compose the full template
        script_content = self.composition_engine.compose(
            context=variables,
            execution_context=self.execution_context
        )
        
        # Cleanup
        self.composition_engine.blocks.pop("user_commands", None)
        
        return script_content
```

## 7. Legacy Code Analysis and Cleanup Plan

### 7.1 ConfigManager Analysis

#### 7.1.1 Current ConfigManager Architecture

The current ConfigManager (`benchpro/config/config_manager.py`) serves as a global service responsible for:

1. **Loading configs**: from YAML files
2. **Merging configs**: from various sources (defaults, user configs, CLI overrides)
3. **Schema validation**: ensuring configs meet expected schemas
4. **Path resolution**: handling relative and absolute paths
5. **System-wide settings**: managing global configuration settings

Its primary interfaces include:
- `load_config(config_path)`
- `get_merged_config(cli_params)`
- `validate_config(config)`
- `resolve_paths(config, base_path)`

#### 7.1.2 Relationship to New Architecture

The new component-based architecture has introduced:
- `ConfigComponent` interface: defining the contract for configuration components
- `YamlConfigComponent`: implementing the interface for YAML configuration files

This creates a potential duplication with the existing ConfigManager. However, they serve different purposes:
- `ConfigManager`: Global service, system-wide settings, validation
- `YamlConfigComponent`: Task-specific, pluggable component, focused responsibility

### 7.2 Consolidation Plan

To avoid duplication and ensure clean code, we'll implement the following strategy:

1. **Extract Reusable Logic**:
   - Identify common functionality between ConfigManager and YamlConfigComponent
   - Extract into utility functions in a shared module (e.g., `benchpro/utils/config_utils.py`)
   - Ensure both implementations use these shared utilities

2. **Phase-out Strategy**:
   - Identify parts of the codebase still dependent on ConfigManager
   - Gradually replace with dependency injection of appropriate components
   - Create adapters where necessary for backward compatibility

3. **Component-ize ConfigManager**:
   - Refactor ConfigManager to internally use YamlConfigComponent
   - Make ConfigManager a facade over component-based implementation
   - Deprecate direct usage in favor of component injection

4. **Timeline**:
   - Keep both implementations during transition (Phase 1-3)
   - Deprecate old implementation after all usages converted (Phase 4)
   - Remove deprecated code in a cleanup phase (Phase 5)

### 7.3 Template System Cleanup

Similarly, for the template system:

1. **Template Engine Consolidation**:
   - Identify overlap between old `TemplateEngine` and new block-based system
   - Extract shared utilities (e.g., Jinja environment setup) to avoid duplication
   - Create adapters to make old code use new components internally

2. **Gradual Replacement**:
   - Replace usages of `TemplateEngine` with appropriate script generators
   - Update task orchestration code to use new components
   - Ensure tests cover both implementations during transition

3. **Final Cleanup**:
   - Remove legacy template code once all usage points are converted
   - Document new template system thoroughly in user and developer guides
   - Ensure all examples use the new system
